# VIP API — Phase B4 Connections and Secrets

The B8 shared jobs, workers, files, secure downloads, and real-time event architecture is documented
in [ASYNC_JOBS_FILES_EVENTS.md](../../docs/backend/ASYNC_JOBS_FILES_EVENTS.md).

This application contains B0 platform foundations, B1 first-party authentication, B2 explicit
multi-tenancy, and B3 server-authoritative roles, permissions, flags, entitlements, quotas, and
persistent audit events. SSO, MFA, billing, custom roles, and business domains remain out of scope.
See [the governance architecture](../../docs/backend/GOVERNANCE.md).

B4 adds tenant-owned live connections, strict connection-type schemas, AES-GCM encrypted
credential versions, secure server-side testing, and SSRF controls. See
[connections and secrets](../../docs/backend/CONNECTIONS_AND_SECRETS.md). Run
`python -m vip_api.cli seed-connection-types` after migrations.

## Repository assessment and decisions

Before Phase B0, the repository contained a Vue 3/Vite frontend at the root and no backend,
Python package, Docker configuration, migration environment, or backend CI. The frozen frontend
architecture already defined `/api/v1`, `X-Correlation-Id`, PostgreSQL, Redis, safe error handling,
and structured observability as target conventions. Existing frontend source, contracts, npm
tooling, and the frontend CI jobs were preserved. The backend therefore lives at `apps/api`; the
root Compose file and CI workflow are the only cross-application integration points.

## Requirements

- Python 3.12 (3.13/3.14 are accepted for native tooling where dependencies provide wheels)
- Docker Desktop with Docker Compose
- PostgreSQL 17 and Redis 8 when running services natively

## Native development

From `apps/api`:

```bash
python -m venv .venv
# PowerShell: .venv\Scripts\Activate.ps1
# POSIX: source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.lock
python -m pip install --no-deps -e .
cp .env.example .env              # PowerShell: Copy-Item .env.example .env
```

Edit `.env` with a local-only database password. Settings are loaded by `pydantic-settings` from
process environment variables first and `apps/api/.env` second. Required database and Redis URLs
fail validation clearly when absent. URLs are held as secret values and are never emitted through
API responses or normal logs.

Start only infrastructure from the repository root:

```bash
docker compose up -d postgres redis
```

For native API execution, the example URLs use `localhost`. Then run:

```bash
cd apps/api
alembic upgrade head
uvicorn vip_api.main:app --reload --no-access-log
```

## Docker Compose development

From the repository root:

```bash
docker compose config
docker compose up --build
docker compose logs -f api
docker compose down
```

Compose supplies container hostnames (`postgres`, `redis`) and development-only credentials. Set
`POSTGRES_PASSWORD` in a root `.env` to replace the local fallback. Named volumes preserve both
PostgreSQL and Redis data. The API waits for healthy dependencies, applies migrations, drops to a
non-root user, and then starts Uvicorn with reload only in development.

## Migrations

Run from `apps/api` with `DATABASE_URL` configured:

```bash
alembic upgrade head
alembic current
alembic revision --autogenerate -m "concise_snake_case_change"
alembic downgrade -1
```

Use revision filenames shaped as `YYYYMMDD_NNNN_concise_snake_case.py`. Review every autogenerated
migration. Take a backup and inspect downgrade code before downgrading any shared environment. The
B0 revision creates no domain table. Revision `20260721_0002` adds only authentication-owned
`users`, `auth_sessions`, and `password_reset_tokens` tables plus the user-status enum. Revision
`20260721_0003` adds organizations, workspaces, explicit memberships, invitations, composite tenant
constraints, and the single-default-workspace invariant.

## Tenancy architecture

The organization is the primary tenant boundary. Workspace access is explicit and always checked
inside its parent organization. Management endpoints use organization/workspace path IDs; future
tenant-scoped product endpoints receive `X-Organization-ID` and `X-Workspace-ID`. Both are untrusted
input. `/api/v1/tenant-context` demonstrates authenticated membership resolution. Unauthorized
scoped lookups return non-disclosing 404 responses.

Every tenant-owned repository call requires `organization_id`; workspace-owned calls require both
IDs. Updates, deletes, counts, and joins are tenant filtered. Validated tenant and membership IDs are
bound to request-scoped structured logs. Future Redis keys must include the configured prefix,
organization, and workspace where applicable.

Invitations store only a domain-separated SHA-256 token hash, expire, can be revoked, require the
authenticated email to match, and are consumed transactionally. Development/test responses may
return the token as a delivery substitute; staging/production never do. Memberships reference
scoped B3 system roles and the migration safely maps every former coarse B2 role.

The frontend fetches only authorized organizations/workspaces, treats persisted IDs as preferences,
revalidates them after login/reload, clears workspace state before organization switches, and scopes
business cache/storage by user, organization, and workspace. Logout clears tenant state.

Developer security rule: every new tenant-owned table, query, cache key, event, job, and API endpoint
must explicitly include and validate organization context. Workspace-owned operations must also
include workspace context.

### Development tenant fixture

Supply three password values through process environment or a secret manager, never command-line

```bash
VIP_DEMO_USER_A_PASSWORD='...' VIP_DEMO_USER_B_PASSWORD='...' \
VIP_DEMO_USER_C_PASSWORD='...' python -m vip_api.cli seed-multitenancy-demo
python -m vip_api.cli cleanup-multitenancy-demo
```

The development/test-only seed is idempotent. It creates Alpha/Beta, two workspaces each, Users

### Tenancy endpoints

```text
GET|POST   /api/v1/organizations
GET|PATCH  /api/v1/organizations/{organization_id}
GET|POST   /api/v1/organizations/{organization_id}/workspaces
GET|PATCH  /api/v1/organizations/{organization_id}/workspaces/{workspace_id}
GET|PATCH|DELETE /api/v1/organizations/{organization_id}/members[/{membership_id}]
GET|POST|DELETE  /api/v1/organizations/{organization_id}/workspaces/{workspace_id}/members[/{membership_id}]
GET|POST|DELETE  /api/v1/organizations/{organization_id}/invitations[/{invitation_id}]
POST       /api/v1/invitations/accept
GET        /api/v1/tenant-context
```

Unsafe requests require the B1 CSRF cookie/header. A 400 tenant error indicates missing, malformed,
or duplicate headers. A non-disclosing 404 means the tenant is absent, inactive, or unauthorized.
The frontend discards stale persisted selections during the next tenancy bootstrap.

## Authentication development

Create an initial user without putting the password in shell history:

```bash
python -m vip_api.cli create-user --email admin@example.test --display-name "Local Admin"
```

The CLI prompts twice with terminal echo disabled. Automation may pipe exactly one secret line and
add `--password-stdin`; never pass passwords as command arguments or commit development passwords.

Browser sessions use three cookies: `vip_access_session` and `vip_refresh_session` are `HttpOnly`;
`vip_csrf_token` is readable by the frontend for double-submit CSRF validation. Raw session and
password-reset tokens are never stored in PostgreSQL—only domain-separated SHA-256 hashes are.
Unsafe authenticated requests require the CSRF cookie/header pair and a trusted `Origin`/`Referer`
when supplied. Cookie names, paths, SameSite policy, Secure flag, session TTLs, lockout thresholds,
trusted frontend origins, and rate limits are environment-configurable. Production validation
requires secure cookies and rejects wildcard CORS/CSRF origins.

Authentication endpoints:

```text
POST /auth/login    JSON: {"email":"...","password":"..."}
GET  /auth/me
POST /auth/refresh  X-CSRF-Token: value from vip_csrf_token cookie
POST /auth/logout   X-CSRF-Token: value from vip_csrf_token cookie
```

Login errors intentionally do not distinguish unknown users, wrong passwords, or locked accounts.
Refresh rotates the complete session and rejects replay by revoking its rotation chain. Logout is
idempotent. Password reset storage and one-time consumption are implemented as an internal service;
public reset/email delivery endpoints are deliberately deferred.

User status is enforced on every login and authenticated request. `active` users may authenticate;
`locked` users remain denied until their UTC lock expiry; `pending`, `disabled`, `suspended`, and
`deleted` users are denied. Failed passwords increment a persistent counter, the configured
threshold temporarily locks the account, and successful login resets the counter.

Operator commands:

```bash
python -m vip_api.cli revoke-all-sessions --email admin@example.test
python -m vip_api.cli cleanup-expired-sessions
```

Password changes call the same all-session revocation service. The password-reset foundation uses
hashed, expiring, single-use tokens and generic unknown-email behavior. Delivery and public reset
routes are intentionally deferred until an email provider and product flow exist.

## Deployment examples

Local HTTP development uses explicit origins, credentialed CORS, `AUTH_COOKIE_SECURE=false`, and
`AUTH_COOKIE_SAMESITE=lax` as shown in `.env.example`. For staging or production, use HTTPS and
values matching the real deployment topology, for example:

```env
# app.staging.example.com -> api.staging.example.com
APP_ENV=staging
FRONTEND_URL=https://app.staging.example.com
CORS_ALLOWED_ORIGINS=https://app.staging.example.com
CORS_ALLOW_CREDENTIALS=true
CSRF_TRUSTED_ORIGINS=https://app.staging.example.com
AUTH_COOKIE_SECURE=true
AUTH_COOKIE_SAMESITE=lax
AUTH_COOKIE_DOMAIN=.staging.example.com

# app.example.com -> api.example.com
APP_ENV=production
FRONTEND_URL=https://app.example.com
CORS_ALLOWED_ORIGINS=https://app.example.com
CORS_ALLOW_CREDENTIALS=true
CSRF_TRUSTED_ORIGINS=https://app.example.com
TRUSTED_HOSTS=api.example.com
AUTH_COOKIE_SECURE=true
AUTH_COOKIE_SAMESITE=lax
AUTH_COOKIE_DOMAIN=.example.com
```

Prefer a same-site frontend/API deployment. Use `SameSite=None` only for a deliberately cross-site
HTTPS architecture; configuration validation requires `Secure=true`. Production also requires
explicit trusted hosts and rejects wildcard CORS/CSRF origins.

## Tests and quality gates

Unit tests do not require Docker:

```bash
pytest -m "not integration"
```

With PostgreSQL and Redis available and the test URLs exported:

```bash
# PowerShell
$env:RUN_INTEGRATION_TESTS="1"
$env:DATABASE_URL="postgresql+asyncpg://vip:vip_local_dev_only@localhost:5432/vip_test"
$env:REDIS_URL="redis://localhost:6379/15"

# POSIX uses equivalent `export` commands.
```

The migration integration test refuses to run unless the database name ends in `_test`, because it
validates a real downgrade to base before upgrading to head. Clean Compose initialization creates
`vip_test` automatically. For an older existing volume, create it once with
`docker compose exec postgres createdb -U vip vip_test`.

Focused quality commands:

```bash
ruff check .
ruff check . --fix
ruff format --check .
ruff format .
mypy src tests
python scripts/backend_quality.py
```

`requirements.lock` and `requirements.runtime.lock` pin resolved development and runtime dependency
graphs. Regenerate them with Python 3.12 and
`pip-compile --strip-extras --extra dev` / `pip-compile --strip-extras` whenever `pyproject.toml`
constraints change.

From the repository root, `make backend-quality` runs the same gate. When
`RUN_INTEGRATION_TESTS=1`, the single gate also applies migrations and runs all integration tests;
without it, the command explicitly reports that external-service checks were skipped.

## Endpoint examples

```bash
curl -i http://localhost:8000/health
curl -i http://localhost:8000/ready
curl -i http://localhost:8000/api/v1/version
curl -i -H "X-Correlation-ID: local-example" http://localhost:8000/health
```

`/health` is liveness-only and never contacts PostgreSQL or Redis. `/ready` checks both concurrently
with bounded timeouts and returns 503 plus per-dependency `healthy`/`unhealthy` status. The API
accepts a safe `X-Correlation-ID` (1–128 restricted characters), replaces invalid values, always
generates an independent `X-Request-ID`, and returns both headers. Standard error bodies include
the correlation ID.

OpenAPI is enabled by default only in development/test (`/docs`, `/openapi.json`). Production
requires explicit trusted hosts, forbids wildcard CORS origins, disables debug, and disables docs
unless deliberately enabled.

## Troubleshooting

- Database unavailable: confirm `docker compose ps`, the database hostname in `DATABASE_URL`, and
  `docker compose logs postgres`. Native processes use `localhost`; containers use `postgres`.
- Redis unavailable: check `docker compose exec redis redis-cli ping` and the equivalent host rule.
- Migration connection error: run `alembic` from `apps/api`, where `alembic.ini` and `.env` live.
- Port collision: set `API_PORT`, `POSTGRES_PORT`, or `REDIS_PORT` in the root `.env`.
- Readiness 503 while health is 200: the process is alive but at least one required dependency is
  unavailable; inspect the non-sensitive readiness check and container logs.
- Browser login network error: confirm the exact frontend origin is in `CORS_ALLOWED_ORIGINS`,
  `CORS_ALLOW_CREDENTIALS=true`, the client uses `credentials: include`, and API preflight permits
  the configured CSRF/context headers.
- `CSRF_VALIDATION_FAILED`: confirm the readable CSRF cookie is sent through the configured header,
  the request `Origin` is in `CSRF_TRUSTED_ORIGINS`, and cookie domain/path settings match the API.
- To test expiry safely, use the integration suite (`pytest -m integration`), which moves test-only
  session timestamps into the past. Do not alter shared or production session timestamps manually.
- If cookies appear stale after changing names/domains/paths, clear the old browser cookies once;
  logout can only delete cookies using the currently configured attributes.
